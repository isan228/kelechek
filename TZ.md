## 1. Общие сведения, цели, философия, границы MVP

### 1.1. Назначение

Сервис мотивирует людей **продолжать заниматься спортом** для здоровья. Часть стоимости месячного абонемента зачисляется занимающемуся на накопительный баланс, который позиционируется как **помощь в оплате образования** (университет, ПТУ и аналогичные заведения).

Интерфейс строится вокруг **накопления, серии и цели**, а не вокруг «кэшбэка», «бонусов» и «скидок».

### 1.2. Цели продукта

1. Стимулировать регулярную оплату занятий.
2. Накапливать целевую сумму на образование по прозрачным правилам.
3. Дать занимающемуся контроль: баланс, история, прогресс к праву на вывод.
4. Обеспечить тренеру инструменты классов, приглашений и посещаемости **без доступа к деньгам**.
5. Дать оператору журналы, сверку, выгрузку в бухгалтерию и администрирование заявок.
6. Удерживать самостоятельно занимающихся через базу тренировочного контента.

### 1.3. Масштаб

| Параметр | Значение |
|----------|----------|
| Занимающиеся | до 200 000 |
| Тренеры | до 3 000 |
| Платежи, оценка | **[ДОПУЩЕНИЕ]** ~2,4 млн / год |
| Проводки, оценка | **[ДОПУЩЕНИЕ]** ~7 млн / год |
| Накопительно за 3 года | свыше 20 млн записей журналов |
| Пик нагрузки | начало календарного месяца (оплаты продления) |

### 1.4. Границы системы

Система **делает:** приём оплаты абонемента, атомарное распределение долей, журналы баланса занимающегося и начислений тренеру, заявки на вывод, учёт занятий, классы, контент, выгрузку расчётной базы.

Система **не делает:** расчёт налогов и отчислений; определение итоговой зарплаты тренера; выплату тренеру; хранение полных реквизитов карт; медицинские консультации; банковский эквайринг «внутри» (только интеграция).

### 1.5. Что не входит в MVP

**Продукт / финансы**

- Нативный iOS/Android-клиент.
- Рекуррентное списание без участия пользователя (автопродление токеном) — **[ДОПУЩЕНИЕ: в MVP пользователь инициирует оплату сам]**; токенизация карт закладывается.
- Несколько одновременных активных тренеров.
- Гостевые занятия у чужого тренера.
- Промокоды, скидки, семейные тарифы, корпоративные договоры.
- Чат занимающийся–тренер.
- Публичный каталог тренеров и «маркетплейс».

**Выплаты**

- Реализация гранта учебному заведению (интерфейс провайдера и справочник вузов — **в модели есть**, UI и интеграция гранта в MVP нет).
- Частичная выплата нескольких назначений в одной заявке.

**Контент: только модель данных, без реализации в MVP**

| Функция | В модели | В MVP |
|---------|----------|-------|
| Отметка о прохождении тренировки | да | нет |
| Персональные подборки | да | нет |
| Оценки и комментарии | да | нет |
| История просмотров | да | нет |
| Рекомендации | да | нет |
| Контент от тренера | поле автора + роль | нет |
| Льготный период после оплаты | конфигурация | выключен |
| Ознакомительные материалы без оплаты | флаг `accessPolicy` | выключен |
| Уровни доступа по типам контента | `ContentAccessRule` | выключены |
| Непрерывность серии как условие вывода | правило `PAYMENT_STREAK` | выключено, структура есть |

**Тренер**

- Лимит активных подопечных — выключен.
- Экраны денег, заявки на вывод, реквизиты тренера — **не проектируются**.

### 1.6. Принцип разделения механик (обязателен для реализации)

**Начисление на баланс занимающегося происходит сразу при успешной оплате и не зависит от посещений.**

Причина: сервис допускает самостоятельные тренировки без тренера; факт таких тренировок непроверяем. Условие начисления «по посещениям» дискриминировало бы эту категорию.

Посещаемость фиксируется тренерами и служит **основанием для оплаты труда тренеров бухгалтерией заказчика**. На баланс занимающегося посещаемость **не влияет**. Запрещено связывать эти механики в одном сервисе начисления, в одном задании очереди или в одном инварианте «нет отметки — нет доли».

## 2. Глоссарий

| Термин | Определение |
|--------|-------------|
| **Баланс** | Доступная сумма целевой поддержки занимающегося. Вычисляется как сумма подписанных проводок журнала занимающегося минус активные холды. Не хранится как изменяемое поле-истина. |
| **Начисление** | Проводка с положительным знаком в журнале занимающегося или журнале тренера, порождённая успешным платежом (или корректировкой администратора). |
| **Право на вывод** | Состояние, при котором все **активные** на момент подачи правила условий вывода выполнены. Не равно «баланс > 0». |
| **Серия** | Число непрерывных календарных месяцев, в каждом из которых есть хотя бы один успешный платёж, покрывающий хотя бы один день этого месяца. Отображается пользователю как прогресс регулярности, не как кэшбэк. |
| **Выплата** | Исполнение одобренной заявки через модуль payout provider (в MVP — перевод на карту). |
| **Грант** | Будущий способ выплаты: перечисление напрямую учебному заведению. В ядре расчёта не участвует. |
| **Абонемент** | Право доступа на оплаченный интервал дат `[startsAt, endsAt]` включительно, порождённое успешным платежом по тарифу. |
| **Активный пользователь** | Занимающийся, у которого на текущий момент `Asia/Bishkek` существует хотя бы один абонемент со статусом `ACTIVE` и `startsAt ≤ now ≤ endsAt`, не отменённый возвратом. Тренер считается активным для контента **без** абонемента. |
| **Расчётная база тренера** | Внутренняя сумма начислений тренеру за период (журнал тренера) плюс сведения о проведённых занятиях. Не является зарплатой. Доступна только администратору. |
| **Отметка о занятии** | Запись тренера о проведении занятия: дата, класс, состав присутствовавших, статус. Финансово значимые данные. Удаление запрещено. |
| **Единица контента** | Базовая сущность `ContentItem`: упражнение, программа, статья или будущий тип. Общие поля + JSON-тело типа. |
| **Оператор** | Юридическое лицо, удерживающее остаток платежа после долей занимающегося и тренера. |
| **Проводка** | Неизменяемая запись append-only журнала. Исправление — только новой сторнирующей проводкой. |
| **Холд** | Резерв суммы по заявке на вывод; уменьшает доступный баланс, не удаляет начисления. |
| **Связь** | Запись `CoachingRelation` между тренером и занимающимся. Активной одновременно не более одной на занимающегося. |
| **Идемпотентность вебхука** | Повторная доставка события с тем же ключом не создаёт второй платёж и второй набор проводок. |

## 4. Функциональные требования

Формат: пользовательская история + критерии приёмки. Нумерация сквозная.

### 4.1. Учётная запись и локализация

**FR-01. Регистрация занимающегося**  
Как новый пользователь, я регистрируюсь по номеру телефона, чтобы пользоваться сервисом.  
Критерии: OTP; уникальность телефона; язык интерфейса по умолчанию `ru` **[ДОПУЩЕНИЕ Д-12]**; профиль создаётся с ролью `TRAINEE`; согласие с офертой и политикой ПДн фиксируется.

**FR-02. Вход**  
Как пользователь, я вхожу по телефону и OTP.  
Критерии: неуспешный OTP не раскрывает, зарегистрирован ли номер **[ДОПУЩЕНИЕ]**; блокировка после N попыток — **[ДОПУЩЕНИЕ: 5 попыток / 15 мин]**.

**FR-03. Переключение языка**  
Как пользователь, я в любой момент переключаю язык ru/ky, выбор сохраняется в профиле.  
Критерии: все пользовательские строки — из ресурсных файлов; даты, числа, суммы — через локаль; письма и push/SMS на языке получателя из профиля; смена языка не требует перезахода.

**FR-04. Профиль**  
Как занимающийся, я указываю имя, дату рождения, email (необяз.), язык, учебную цель (необяз.).  
Критерии: валидация; изменение ПДн пишется в аудит.

### 4.2. Абонемент и оплата

**FR-05. Просмотр тарифа**  
Как занимающийся, я вижу действующий тариф: срок, цену в сомах, пояснение накопления (без слова «кэшбэк»).  
Критерии: название и описание тарифа — ru и ky; цена целым числом.

**FR-06. Инициация оплаты**  
Как занимающийся, я оплачиваю абонемент через платёжный шлюз.  
Критерии: создаётся `Payment` в статусе `PENDING` с `idempotencyKey`; пользователь уходит на страницу провайдера или виджет; сумма и тариф фиксируются на платеже; повторный клик с тем же ключом не создаёт второй `Payment`.

**FR-07. Успешная оплата**  
Как занимающийся, после успеха я сразу вижу новый оплаченный период и начисление.  
Критерии: вебхук `payment.succeeded` обрабатывается идемпотентно; в одной транзакции БД: статус платежа, интервал абонемента, набор проводок распределения; начисление **не** ждёт посещений; ставка и тренер фиксируются на проводках.

**FR-08. Неуспешная / отменённая оплата**  
Как занимающийся, при отказе я остаюсь без периода и без начисления.  
Критерии: статус `FAILED` / `CANCELED`; проводок нет; можно повторить оплату.

**FR-09. Продление**  
Как занимающийся с действующим периодом, я оплачиваю следующий период заранее.  
Критерии: новый интервал начинается на день после `endsAt` текущего (**Д-03**); серия не прерывается, если нет дыры в календарных месяцах.

**FR-10. Отображение статуса абонемента**  
Как занимающийся, я вижу даты действия и оставшиеся дни.  
Критерии: день истечения включён; таймзона `Asia/Bishkek`; формулировки через i18n plural.

### 4.3. Распределение и баланс

**FR-11. Распределение платежа**  
Как система, я распределяю успешный платёж одной функцией.  
Критерии: см. раздел 5; инвариант суммы; отклонение доли оператора от 18% ≤ 1 сом; покрыто тестами; запрещено дублировать формулу в других модулях.

**FR-12. Экран баланса**  
Как занимающийся, я вижу доступный баланс, холд, всего начислено, цель/прогресс к выводу.  
Критерии: формулировки «накоплено к образованию», не «кэшбэк»; суммы — целые сомы, формат `ru`/`ky`; время отклика — раздел 13.

**FR-13. История операций**  
Как занимающийся, я вижу полный список операций по своему журналу.  
Критерии: начисление, сторно, холд, выплата, корректировка; пагинация; фильтр по типу и периоду; нет возможности удалить запись.

**FR-14. Прогресс к праву на вывод**  
Как занимающийся, я вижу каждое активное условие: выполнено / не выполнено / на проверке, и чего не хватает.  
Критерии: условия читаются из конфигурации, действующей «сейчас» для экрана; для уже поданной заявки показываются **зафиксированные** на заявке результаты.

### 4.4. Вывод

**FR-15. Черновик заявки**  
Как занимающийся, я создаю черновик: сумма, способ выплаты, реквизиты, документы.  
Критерии: набор полей зависит от активного `PayoutMethod`; сумма ≤ доступного баланса; способ из конфигурации.

**FR-16. Подача заявки**  
Как занимающийся, я подаю заявку.  
Критерии: сервер прогоняет все активные правила; по каждому правилу сохраняется результат (`passed` / `failed` / `manual_review`) + снимок конфигурации правила; холд на сумму; статус `SUBMITTED` → при всех авто-проходных формальных — `IN_REVIEW` (ожидает человека по документу) либо `CONDITION_FAILED`.

**FR-17. Рассмотрение администратором**  
Как администратор, я вижу очередь, документ, результаты предпроверки.  
Критерии: массовое одобрение только заявок, прошедших все авто-условия и ожидающих документ; решение и обоснование обязательны при отклонении; SLA — раздел 13.

**FR-18. Исполнение / ошибка выплаты**  
Как система, после одобрения я вызываю payout provider.  
Критерии: статусы `APPROVED` → `PAYOUT_IN_PROGRESS` → `PAID` | `PAYOUT_FAILED`; при ошибке холд сохраняется, заявка доступна к повтору исполнения админом; занимающийся видит статус без банковских внутренних кодов.

**FR-19. Повтор после отклонения**  
Как занимающийся, после `REJECTED` я могу подать новую заявку.  
Критерии: холд снят; причина отклонения видна (локализованный справочник + комментарий); предыдущая заявка неизменна.

### 4.5. Тренер: связь, классы, занятия

**FR-20. Приглашение**  
Как тренер, я приглашаю занимающегося по телефону / ID.  
Критерии: статусы и срок — раздел 8; уведомления на каждый переход; нельзя создать второе активное (`SENT`) приглашение тому же адресату от того же тренера.

**FR-21. Ответ на приглашение**  
Как занимающийся, я принимаю или отклоняю.  
Критерии: при активной связи — явное подтверждение разрыва (Д-07); принятие меняет ставку **со следующего платежа**; прошлые проводки не пересчитываются.

**FR-22. Расторжение**  
Как любая сторона связи или админ, я завершаю связь.  
Критерии: раздел 8; тренерские начисления за уже оплаченные платежи не отзываются.

**FR-23. Классы**  
Как тренер, я создаю класс (название ru/ky, расписание, состав).  
Критерии: в состав можно добавить только активных подопечных этого тренера; поиск и пагинация состава.

**FR-24. Отметка занятия**  
Как тренер, я фиксирую проведение и присутствие в окне Д-14.  
Критерии: вне окна — 403; удаление невозможно; изменение — с аудитом до/после; занимающиеся из состава уведомляются.

**FR-25. Молчаливое принятие отметки**  
Как система, если занимающийся не оспорил отметку за 3 дня, она становится `ACCEPTED`.  
Критерии: джоб идемпотентен; уведомление в момент отметки с дедлайном оспаривания.

**FR-26. Оспаривание**  
Как занимающийся, я оспариваю своё присутствие.  
Критерии: только своя строка; в срок; статус `DISPUTED`; админ решает с обоснованием ru или ky (язык интерфейса админа, текст хранится как введённый + опциональный перевод **[ДОПУЩЕНИЕ: обоснование в языке админа, пользователю показывается as-is с фолбэком]**).

**FR-27. Статистика тренера без денег**  
Как тренер, я вижу число подопечных, посещаемость своих классов, динамику тренировок.  
Критерии: ни одного денежного поля в API; список подопечных — поиск, фильтры, страница.

**FR-28. Лимит подопечных**  
Как система, при включённом лимите я не даю активировать связь сверх `maxActiveTrainees`.  
Критерии: в MVP лимит выключен; счётчик активных связей хранится и обновляется транзакционно.

### 4.6. Администрирование финансов и занятий

**FR-29. Ручная корректировка**  
Как администратор, я создаю корректирующую проводку с обязательной причиной.  
Критерии: не UPDATE существующих строк журнала; аудит; пользователь видит операцию в истории.

**FR-30. Выгрузка расчётной базы**  
Как администратор, я выгружаю период по тренерам для бухгалтерии.  
Критерии: раздел 8.7 и 14.4; период после выгрузки блокируется; повторная выгрузка того же периода даёт тот же идентификатор версии + пометку `reexport`.

**FR-31. Закрытие периода и поправки**  
Как администратор, я вношу корректировку отметки после закрытия отдельной операцией.  
Критерии: попадает в **следующую** выгрузку как adjustment; исходная строка не удаляется.

**FR-32. Отчёты аномалий**  
Как администратор, я вижу: тренеры с подопечными и нулевой активностью; всплеск отметок перед закрытием; высокая доля споров; отметки по подопечным без действующей оплаты в дату занятия.

**FR-33. Сверка**  
Как администратор, я сверяю поступления эквайринга с суммой долей.  
Критерии: поступления = начисления занимающимся + начисления тренерам + доля оператора за период; расхождения — список платежей.

**FR-34. Очередь заявок**  
Как администратор, я фильтрую, сортирую, назначаю заявки на себя/коллегу, выполняю массовые операции.  
Критерии: раздел «Администрирование при массовом потоке».

### 4.7. Контент

**FR-35. Каталог**  
Как пользователь, я вижу каталог: обложки, названия, описания, теги.  
Критерии: без активного абонемента тело и медиа закрыты, CTA «оформить абонемент»; тренер видит тело всегда.

**FR-36. Поиск и фильтры**  
Как активный пользователь, я ищу по названию и фильтрую по тегам/категориям.  
Критерии: поиск по текущему языку + фолбэк; пагинация.

**FR-37. Просмотр единицы**  
Как активный пользователь, я читаю статью / карточку упражнения / программу.  
Критерии: серверная проверка доступа на контент и на каждый медиа-URL; дисклеймер обязателен; для упражнения и программы — поле противопоказаний.

**FR-38. Избранное**  
Как занимающийся, я добавляю единицу в избранное.  
Критерии: список на своём языке; доступен и без активного абонемента (карточки), тело — по правилам доступа.

**FR-39. Управление контентом**  
Как контент-редактор/админ, я создаю черновик, перевожу ru/ky, предпросматриваю, планирую публикацию, публикую после модерации, снимаю, архивирую.  
Критерии: опубликованная версия не меняется черновиком; автор и проверяющий фиксируются; аудит; редактор без доступа к финансам и ПДн.

**FR-40. Быстрое снятие**  
Как модератор, я снимаю материал с публикации без удаления.

**FR-41. Событийные уведомления**  
Как пользователь, я получаю уведомления на языке профиля.

## 5. Финансовая модель и правила расчётов

### 5.1. Независимые журналы

Два append-only журнала:

1. `TraineeLedgerEntry` — баланс занимающегося.  
2. `CoachLedgerEntry` — внутренние начисления тренеру (не зарплата, не вывод).

Баланс / сальдо = сумма `signedAmount` по владельцу (плюс снапшоты, раздел 13). Поле `User.balance` как источник истины **запрещено**.

### 5.2. Структура проводки (общие поля)

| Поле | Тип | Назначение |
|------|-----|------------|
| `id` | UUID | PK |
| `type` | enum | CREDIT_ACCRUAL, DEBIT_REVERSAL, HOLD, HOLD_RELEASE, PAYOUT, ADJUSTMENT, OPERATOR_SHARE (операторский журнал — отдельно, см. 5.3) |
| `amount` | INT | Абсолютная сумма в сомах, ≥ 0 |
| `signedAmount` | INT | Знак учёта: начисление `+amount`, сторно `-amount` |
| `appliedTraineeRateBps` | INT | Ставка занимающегося в базисных пунктах (8200 = 82%), как зафиксирована |
| `appliedCoachRateBps` | INT | 0 или 5000 |
| `sourceType` / `sourceId` | | Платёж, заявка, админ-корректировка |
| `paymentId` | FK nullable | Платёж-источник |
| `linkedEntryId` | FK nullable | Связанная проводка (сторно ↔ оригинал, доли одного распределения) |
| `distributionGroupId` | UUID | Общий id набора долей одной транзакции |
| `coachId` | FK nullable | Тренер, **зафиксированный в момент транзакции** |
| `coachingRelationId` | FK nullable | Связь на момент транзакции |
| `actorId` | FK nullable | Пользователь или `SYSTEM` |
| `createdAt` | timestamptz | Неизменяемо |

Записи не обновляются и не удаляются (кроме разделов партиционирования — перенос в архив без изменения содержимого).

### 5.3. Журнал оператора

Доля оператора пишется в `OperatorLedgerEntry` в той же БД-транзакции, чтобы сверка не вычисляла остаток «платёж − две доли» в уме. Это третья нога инварианта, не «баланс пользователя».

### 5.4. Ставки

Справочник `RatePlan`: `traineeSoloBps = 8200`, `traineeWithCoachBps = 3200`, `coachBps = 5000`.  
Ставки **копируются на платёж и проводки** в момент успеха. Изменение справочника не пересчитывает прошлое.

Операторская доля **не хранится как ставка 18%**: она всегда остаток.

### 5.5. Единая функция распределения

Псевдокод (единственное место расчёта, unit-тесты обязательны):

```
roundHalfUp(x) = floor(x + 0.5)  // x ≥ 0

distribute(amountSom: int, hasActiveCoach: bool) ->
  { trainee, coach, operator }

  assert amountSom ≥ 0 and integer
  traineeRate = hasActiveCoach ? 0.32 : 0.82
  trainee = roundHalfUp(amountSom * traineeRate)
  coach   = hasActiveCoach ? roundHalfUp(amountSom * 0.50) : 0
  operator = amountSom - trainee - coach

  assert trainee + coach + operator == amountSom
  assert abs(operator - amountSom * 0.18) ≤ 1
  return { trainee, coach, operator }
```

Реализация: один модуль `finance/distributePayment.ts` (+ зеркало в SQL-тестах при необходимости). Запрещено считать доли в контроллерах вебхука, в UI, в отчётах.

`hasActiveCoach` определяется **на момент успешной транзакции**: существует `CoachingRelation` со статусом `ACTIVE` у плательщика. Id тренера и связи копируются на `Payment` и проводки. Позднейшее расторжение **не меняет** уже созданные проводки.

### 5.6. Атомарность

Одна успешная оплата в одной транзакции БД (`SERIALIZABLE` или `REPEATABLE READ` + уникальные ограничения **[ДОПУЩЕНИЕ: REPEATABLE READ + идемпотентный ключ]**):

- `Payment.status = SUCCEEDED`
- `MembershipPeriod` создан
- 1 проводка занимающегося (CREDIT)
- 0 или 1 проводка тренера (CREDIT)
- 1 проводка оператора
- все с одним `distributionGroupId`

Либо все, либо откат. Частичное начисление недопустимо.

### 5.7. Идемпотентность вебхуков

Уникальный ключ: `provider + providerEventId` (таблица `ProcessedWebhook`).  
Повтор: HTTP 200, без новых проводок.  
Конкурирующие доставки: уникальный индекс, второй транзакции — no-op.

Дополнительно: уникальный индекс `(paymentId, type)` на начислении CREDIT по платежу, чтобы двойной внутренний вызов тоже не прошёл.

### 5.8. Возвраты, отмены, chargeback

| Событие | Действие |
|---------|----------|
| Отмена до успеха | Статус CANCELED, проводок нет |
| Возврат после успеха | Сторно **всех** проводок группы (занимающийся, тренер, оператор) на исходные суммы; период абонемента `REFUNDED`; доступ пересчитывается (Д-10) |
| Сторно, если по занимающемуся уже есть холд/выплата | Сначала сторно доступного; если `available + holds < reversal` — снять неисполненные холды; если выплата уже `PAID` и остатка не хватает — проводка `DEBIT_REVERSAL` на доступный остаток + запись `UserDebt` на недостачу; тренерская проводка сторнируется полностью всегда (это внутренний учёт). **[ДОПУЩЕНИЕ Д-06]** |
| Тренер в проводке ≠ текущий тренер | Сторно идёт на `coachId` **проводки**, не на текущего |

Прошлое начисление **никогда** не «переезжает» другому тренеру.

### 5.9. Снапшоты остатков

Периодический снапшот (`BalanceSnapshot`) по каждому владельцу журнала: `asOf`, `sumSigned`, `entryIdTo`. Экран баланса читает последний снапшот + хвост журнала после него. Полный пересчёт из журнала — админ-операция сверки.

### 5.11. Жизненный цикл заявки на вывод

```
DRAFT → SUBMITTED → CONDITION_CHECK
                      ├─ CONDITION_FAILED (можно вернуться в DRAFT / новая заявка)
                      └─ IN_REVIEW
                            ├─ REJECTED (холд снят)
                            ├─ NEED_INFO (холд сохранён, пользователь догружает)
                            └─ APPROVED → PAYOUT_IN_PROGRESS
                                            ├─ PAID (холд закрыт выплатой)
                                            └─ PAYOUT_FAILED (холд сохранён, повтор исполнения)
```

- Холд создаётся при переходе в `SUBMITTED`.  
- Срок холда: **[ДОПУЩЕНИЕ]** 30 календарных дней; по истечении, если не `PAID` и не в работе выплаты — авто-`EXPIRED`, холд снимается, заявка закрывается, пользователь уведомляется.  
- Изменение конфигурации условий **не** пересчитывает уже поданные заявки: на заявке хранится JSON-снимок правил и результатов.  
- Параллельно две заявки `SUBMITTED`/`IN_REVIEW`/`APPROVED`/`PAYOUT_IN_PROGRESS` у одного пользователя **запрещены** (уникальный частичный индекс).

## 6. Условия вывода и конфигурируемость

### 6.1. Принцип

Условия юридически не финализированы. Реализуется **набор правил**, не жёсткий `if` в коде заявки.

- Справочник типов правил (код обработчика).  
- Экземпляры в `WithdrawalPolicy` (версия, дата действия, `isActive`).  
- Каждая заявка копирует `policyVersion` + массив `conditionResults`.  
- Новая версия политики не трогает старые заявки.  
- Экран «прогресс к выводу» использует **текущую** активную политику.

### 6.2. Типы правил MVP и задел

| Код | Описание | MVP |
|-----|----------|-----|
| `HOLDING_PERIOD` | N месяцев с даты **первого** начисления `CREDIT_ACCRUAL` | да, N=12 **[Д-16]** |
| `MIN_AMOUNT` | Сумма заявки ≥ минимума и ≤ available | да, 1000 KGS **[Д-16]** |
| `ENROLLMENT_DOCUMENT` | Загружена справка, статус документа `VERIFIED` | да (человек проверяет файл; формальные — авто) |
| `PAYMENT_STREAK` | Нет разрыва помесячной оплаты | структура да, **выключено** |
| `KYC_COMPLETE` | ПИН/паспорт верифицированы | **[ДОПУЩЕНИЕ]** включено перед первой выплатой |
| `NO_OPEN_DEBT` | Нет `UserDebt` | да |
| `ACTIVE_PAYOUT_REQUISITE` | Реквизиты способа выплаты валидны | да |

Обработчик правила: `{ code, evaluate(user, application): ConditionResult }`.  
`ConditionResult`: `passed` | `failed` | `manual_review`, `details` (JSON, без секретов), `evaluatedAt`.

Формальные (`HOLDING_PERIOD`, `MIN_AMOUNT`, `NO_OPEN_DEBT`, `PAYMENT_STREAK` если вкл.) гоняются **до** очереди человека. Человек в MVP проверяет **документ** и соответствие личности.

### 6.3. Правило серии (заложено, в MVP выключено)

**Разрыв:** календарный месяц (январь, февраль, …) в `Asia/Bishkek`, в котором **нет** ни одного `Payment.status = SUCCEEDED`, чей `MembershipPeriod` пересекается хотя бы одним днём с этим месяцем. Месяцы **до** первого успешного платежа пользователя в разрыв не считаются (серия ещё не начата).

**После разрыва:**

| Что | Поведение **[Д-15]** |
|-----|----------------------|
| Накопленный баланс | **Заморозка права на вывод по серии**, сумма **не сгорает** |
| Счётчик серии | Сброс в 0 |
| Частичное сгорание | Не применяется (если понадобится — отдельный тип правила и проводка `BURN`, в MVP нет) |

**Отображение:** «Серия: N месяцев подряд». При разрыве: «Серия прервана в {месяц}». Прогресс-бар серии отделён от баланса. Пользователю явно: накопленное сохранено, для условия непрерывности серию нужно начать заново.

Покрытие месяца: достаточно оплаты, чей период задевает месяц (в т.ч. период 15.01–13.02 покрывает январь и февраль).

### 6.4. Документ об обучении

- Типы: справка о зачислении / студенческий / иной код из справочника (ru/ky названия причин и типов).  
- Файл: PDF/JPEG/PNG, **[ДОПУЩЕНИЕ]** до 10 МБ.  
- Язык документа — любой (ru, ky, иной); перевода не требуем.  
- Срок годности справки: **[ДОПУЩЕНИЕ]** 90 дней с даты выдачи на документе (поле, вводит админ при проверке) либо 90 дней с загрузки, если даты нет.  
- Поддельная / просроченная: статус `REJECTED`, причина из справочника, заявка `REJECTED` или `NEED_INFO`.

### 6.5. Изменение конфигурации

Админ создаёт новую `WithdrawalPolicyVersion`. Старая остаётся для истории. Активна одна. Уже поданные заявки сравниваются только со своим снимком.

## 7. Архитектура выплат (заменяемый модуль)

### 7.1. Разделение

Ядро (оплата, `distribute`, журналы, холды, условия) **не знает** банка и не знает, карта это или вуз.

```
WithdrawalApplication
        │
        ▼
PayoutProvider (интерфейс)
        │
        ├── CardTransferProvider      ← MVP
        └── InstitutionGrantProvider  ← заглушка + контракт
```

Интерфейс (минимум):

```
createPayout(application): { providerRef }
getStatus(providerRef): { status, raw }
cancel?(providerRef)
parseWebhook(payload, signature)
requiredFields(method): FieldSpec[]
requiredDocuments(method): DocType[]
```

Переключение способа: `SystemConfig.activePayoutMethod = CARD | GRANT`.  
Не требует миграции журналов. Заявка хранит `method` и `requisites` JSONB по схеме метода.

### 7.2. Реквизиты

**CARD (MVP):** `cardToken`, `cardMask` (например `*1234`), `cardBrand`, `holderName` (если требует банк). Номер карты в открытом виде **не хранить**.

**GRANT (будущее):** `institutionId`, `studentIdAtInstitution`, `purpose` (учебный год / семестр), пакет документов вуза. Справочник `EducationInstitution` (ru/ky название, БИН, реквизиты выплаты юрлицу, `isActive`) закладывается сразу.

Валидация реквизитов — стратегия провайдера, не общее ядро.

### 7.3. Заявка и документы по способу

Таблица `PayoutMethodSchema`: метод → список обязательных полей и `DocumentType`. UI и API читают схему. Добавление метода = новая реализация + строка схемы, без ломки `WithdrawalApplication`.

### 7.4. Идемпотентность выплаты

Ключ: `withdrawalApplicationId`. Повторный вызов провайдера с тем же ключом не создаёт второй перевод.

## 8. Связь «тренер — занимающийся», приглашения, учёт занятий

### 8.1. Кардинальность

- У занимающегося **не более одной** активной связи.  
- У тренера — неограниченно (пока не включён лимит Д-17).  

Гарантия БД, не только UI:

```
CREATE UNIQUE INDEX coaching_relation_one_active_trainee
ON coaching_relations (trainee_id)
WHERE status = 'ACTIVE';
```

Счётчик `Coach.activeRelationCount` обновляется в той же транзакции, что смена статуса связи. Лимит: `IF config.maxActiveTrainees IS NOT NULL AND count >= max THEN abort`.

### 8.2. Приглашения

Статусы: `SENT` → `ACCEPTED` | `DECLINED` | `REVOKED` | `EXPIRED`.

| Параметр | Значение |
|----------|----------|
| Срок жизни | **[Д-13]** 7 суток с `createdAt` |
| Кто отправляет | Тренер (админ может от имени — **[ДОПУЩЕНИЕ: нет в MVP]**) |
| Кто отзывает | Отправитель, пока `SENT` |
| Повтор | После EXPIRED/DECLINED/REVOKED — новое приглашение |

**Отправка, если у адресата уже есть тренер:** **разрешена**. Тренер видит предупреждение: «У пользователя уже есть тренер». Имя текущего тренера **другому тренеру не показываем** **[ДОПУЩЕНИЕ]**.

**Принятие при активной связи:** не молча. Экран: «Текущая связь с {имя} будет завершена. Ставка накопления со **следующего** платежа изменится.» Два шага (кнопка «Продолжить» + «Подтвердить»). В одной транзакции: старая связь `ENDED` (`endReason = REPLACED`), новая `ACTIVE`, приглашение `ACCEPTED`.

**Занимающийся без связи:** принятие сразу создаёт `ACTIVE`.

**Нельзя принять**, если: приглашение не `SENT`; истекло; тренер деактивирован; включён лимит подопечных и он исчерпан — тогда ошибка с понятным кодом.

### 8.3. Расторжение

| Кто | Подтверждение второй стороны |
|-----|------------------------------|
| Занимающийся | Не требуется **[ДОПУЩЕНИЕ]** |
| Тренер | Не требуется **[ДОПУЩЕНИЕ]** |
| Админ (принудительно) | Не требуется, причина обязательна |

После расторжения ставка занимающегося со **следующего платежа** = 82%, тренерской доли нет.

Уведомления: обе стороны, все переходы приглашения и `ENDED`.

### 8.4. Финансовые последствия связи — однозначно

**Рекомендуемое и принятое правило: новая ставка с ближайшего следующего платежа. Прошлые начисления не пересчитываются.**

Обоснование:

1. Платёж уже распределён атомарно; пересчёт ломает сверку с эквайрингом и выгрузки в бухгалтерию.  
2. Самостоятельные и «с тренером» должны иметь предсказуемый момент смены, иначе спор «кто получил 50% за уже оплаченный месяц».  
3. Посещения не связаны с начислением занимающемуся; менять долю задним числом из-за связи было бы той же ошибкой, что привязка к посещениям.

| Ситуация | Правило |
|----------|---------|
| Момент ставки | Успех транзакции оплаты: читается активная связь **сейчас** |
| Фиксация тренера | `Payment.coachId`, проводки `coachId` + `coachingRelationId` |
| Расторжение в середине оплаченного периода | Начисленное тренеру **не отзывается**; следующие платежи — без него |
| Приглашение принято в день оплаты | Если принятие **раньше** коммита вебхука успеха — ставка 32% и этот тренер; если **позже** — платёж уже с 82% или со старым тренером. Гонка: вебхук и accept сериализуются по `userId` (advisory lock). |
| Возврат после расторжения | Сторно на тренера из **проводки** |
| Удаление/блокировка тренера | Связи `ENDED` причиной `COACH_DEACTIVATED`; непринятые приглашения `REVOKED`; невыплаченные (внутренние) начисления остаются в журнале для выгрузки; новый кредит этому тренеру не создаётся |

### 8.5. Классы и состав

- Класс принадлежит одному тренеру.  
- Названия ru/ky.  
- Состав: только активные подопечные этого тренера (Д-08).  
- Расписание: слоты (день недели / конкретные даты) **[ДОПУЩЕНИЕ: конкретные сессии `ClassSession` с датой-временем]**.  
- Занимающийся видит свои классы и расписание.

### 8.6. Отметки как финансово значимые данные

| Правило | Значение |
|---------|----------|
| Кто ставит | Тренер класса (или админ-корректировка) |
| Окно | Дата сессии (локальная) и **2** дня после (Д-14) |
| Вне окна | Запрет; после закрытия периода — только adjustment |
| Молчаливое принятие | 3 дня без спора → `ACCEPTED` |
| Спор | Занимающийся, только своё присутствие, 3 дня |
| Удаление | Запрещено |
| Изменение | Новый аудит: actor, at, before JSON, after JSON |
| Тренер не видит | Никаких сумм, связанных с отметкой |

Уведомление занимающемуся: «Тренер отметил ваше присутствие {дата, класс}. Оспорить до {дедлайн}.»

Решение админа по спору: `UPHELD` (отметка верна) / `OVERTURNED` (присутствие снято) + `reasonText`.

### 8.7. Вознаграждение тренера и границы системы

Система:

- копит `CoachLedgerEntry`;  
- хранит занятия и отметки;  
- даёт админу сводку за период: расчётная сумма начислений, число проведённых занятий, число активных подопечных, число оспоренных отметок;  
- выгружает CSV и XLSX (оба формата, **[ДОПУЩЕНИЕ]**);  
- **не** считает налоги, **не** считает «к выплате зарплаты», **не** платит тренеру, **не** хранит его карты/счета.

Админ отмечает период: `EXPORTED_TO_ACCOUNTING`, затем `MARKED_PAID_EXTERNALLY` (факт выплаты вне системы).

**Выгрузка**

- Разрез: период `[from, to]`, по тренерам.  
- Идемпотентность: `PayrollExport.version` + hash содержимого. Повтор без изменений — тот же файл/признак `identical`.  
- После `LOCKED` отметки периода не меняются обычным API.

Поля файла (минимум):

`exportId, version, periodFrom, periodTo, coachId, coachName, coachPhone, accrualSumKgs, sessionsCount, attendeesMarkedCount, disputedCount, overturnedCount, activeTraineesAtPeriodEnd, generatedAt`

Лист занятий (второй файл или второй sheet):

`exportId, sessionId, sessionDate, classId, classNameRu, classNameKy, coachId, traineeId, attendanceStatus, disputed, decision, markedAt, locked`

Тренер **не** получает этот файл.

### 8.8. Стимул «набрать подопечных»

- Поле счётчика активных связей.  
- Конфигурируемый лимит (MVP off).  
- Отчёт админа: тренеры с `activeRelationCount > 0` и нулём проведённых занятий / нулём отметок за период.

## 9. Контентная подсистема

### 9.1. Модель единицы

`ContentItem`: `id`, `type` (`EXERCISE` | `PROGRAM` | `ARTICLE` | будущее), `status` (`DRAFT` | `IN_REVIEW` | `SCHEDULED` | `PUBLISHED` | `UNPUBLISHED` | `ARCHIVED`), `authorId`, `reviewerId`, `reviewedAt`, `coverMediaId`, `difficultyTagId` (не жёсткий enum — тег), `publishedAt`, `scheduledAt`, `accessPolicy` (`SUBSCRIBERS` | `FREE_PREVIEW` | `BY_TYPE_RULE`), локализуемые поля в `ContentItemI18n` (`locale` unique per item): `title`, `summary`, `bodyRich`, `contraindications` (обязательно для EXERCISE и PROGRAM).

Тело типа: `ContentItem.body jsonb` по JSON-schema типа. Новый тип = код + schema, без ALTER на колонки упражнения.

**Иерархия программы:** `Program` → `ProgramWorkout[]` → `ProgramWorkoutExercise[]` (`exerciseItemId`, `sets`, `reps`, `restSeconds`, `order`, `notes i18n`). Тренировка программы может ссылаться на `ContentItem` типа EXERCISE.

**Теги и категории:** `Tag`, `TagI18n`, `TagGroup` (мышцы, инвентарь, уровень, цель) — M2M к item. Не enum в Prisma.

**Медиа:** `MediaAsset`: `storageKey`, `mime`, `bytes`, `width`, `height`, `durationMs`, `kind` IMAGE|VIDEO|FILE, `source` UPLOAD|EXTERNAL_URL, `externalUrl`, `variants` (resized).  
**[Д-21]** Видео: загрузка или URL.  
**[ДОПУЩЕНИЕ]** изображения: JPEG/PNG/WebP, длинная сторона ≤ 4096 px, файл ≤ 8 МБ; видео upload ≤ 200 МБ, транскод в 720p mp4; выдача через CDN подписанными URL.

**Версии:** `ContentRevision` (черновик) vs `publishedRevisionId`. Редактирование черновика не меняет published. Публикация атомарно переключает указатель после ревью.

**Двуязычность единицы:** публикация с одним языком **разрешена технически**, но:

- в MVP политика: **[ДОПУЩЕНИЕ]** публиковать можно при наличии `title+body` хотя бы на одном языке; второй — фолбэк Д-12;  
- в админке предупреждение «нет перевода на X»;  
- критерий приёмки краевого случая — см. раздел 10.

Задел без MVP-UI: `ContentCompletion`, `ContentCollection`, `ContentRating`, `ContentComment`, `ContentView`, `ContentRecommendationState`. `ContentCompletion` имеет `userId`, `itemId`, `occurredAt`, `source = SELF_REPORT` — в будущем сигнал вовлечённости самостоятельных, **не** триггер начисления.

### 9.2. Доступ

**Действующий абонемент:** существует `MembershipPeriod` со статусом `ACTIVE`, `timezone Asia/Bishkek`, `startsAt ≤ now ≤ endsAt` (оба конца включительно на границе дня: `endsAt` — конец дня 23:59:59.999 **[ДОПУЩЕНИЕ: хранить timestamptz конца как exclusive `endsAtExclusive` = начало следующего дня, проверка `startsAt ≤ now < endsAtExclusive` — предпочтительно в реализации]**).

День истечения: пользователь **активен весь этот календарный день** в Бишкеке.

| Событие | Доступ к телу |
|---------|----------------|
| Неуспешный платёж | нет (если нет другого периода) |
| Отмена до успеха | нет |
| Возврат за период | период `REFUNDED`, доступ **сразу нет** (Д-10) |
| Истечение во время сессии | следующий запрос API контента/медиа — 403 + код `SUBSCRIPTION_EXPIRED`; клиент закрывает плеер и показывает CTA. Открытая страница не «догоняется» пушем байтов |
| Тренер | доступ есть всегда при роли COACH и `status=ACTIVE` учётки |

Проверка — **одна** функция `assertContentAccess(user, item, media?)`. Все GET контента и медиа-прокси её вызывают. Прямые публичные URL объектов хранилища **запрещены**; только short-lived signed URL **[ДОПУЩЕНИЕ: TTL 10 минут]** после проверки.

Кэш активности: **[ДОПУЩЕНИЕ]** Redis TTL 60 с, ключ `active:{userId}`. Немедленная инвалидация при: успех оплаты, возврат, истечение (джоб по `endsAt`), смена роли, блокировка пользователя.

Каталог без оплаты: список, обложка, title, summary, теги. `body` и медиа-прокси — нет. Поле `accessPolicy=FREE_PREVIEW` позволяет открыть тело без абонемента (MVP все `SUBSCRIBERS`, кроме дисклеймера раздела).

Льготный период, уровни по типам — `ContentAccessRule` JSON в конфигурации, в MVP пусто/выкл.

### 9.3. Управление и ответственность за здоровье

- WYSIWYG (форматированный текст), загрузка медиа, предпросмотр обоих языков, планирование `scheduledAt`, теги, аудит.  
- Публикация только из `IN_REVIEW` после `reviewerId ≠ authorId` **[ДОПУЩЕНИЕ: саморевью админа разрешено, редактора — нет]**.  
- Обязательный дисклеймер в разделе контента и на карточках упражнений (i18n ключи, не из CMS).  
- Поле противопоказаний обязательно для EXERCISE и PROGRAM на каждом языке, на котором есть body.  
- Быстрое `UNPUBLISHED`.  

Юридический риск вреда здоровью — раздел «Риски». Формулировки дисклеймера подлежат юрпроверке.

Роль `CONTENT_EDITOR`: API пользователей, платежей, заявок, документов — 403.

Задел: тренер может быть `authorId`; право `content:propose` выключено.

## 10. Пользовательские сценарии

### 10.1. Happy path (занимающийся самостоятельно)

1. Регистрация, язык ru.  
2. Оплата тарифа 1000 сом.  
3. Распределение: 820 / 0 / 180.  
4. Контент открыт.  
5. Через 12 месяцев и справку — заявка на вывод ≥ 1000, предпроверка OK, админ проверяет документ, перевод на карту, баланс уменьшен.

### 10.2. Happy path (с тренером)

1. Тренер приглашает, занимающийся принимает.  
2. Оплата 1000: 320 / 500 / 180, в проводке `coachId`.  
3. Тренер отмечает занятие, занимающийся не спорит → `ACCEPTED`.  
4. Админ выгружает расчётную базу. Тренер денег в UI не видит.

### 10.3. Краевые случаи

**E-01. Неуспешный платёж**  
Провайдер `failed`. `Payment=FAILED`, периодов и проводок нет, контент закрыт, можно повторить.

**E-02. Дубль вебхука**  
Второй `succeeded` с тем же `providerEventId`: 200, одна группа проводок. Уникальный индекс не даёт второй CREDIT.

**E-03. Возврат после выплаты**  
Заявка `PAID`. Chargeback платежа. Сторно группы. Недостача → `UserDebt`. Доступ к контенту за период снят. Повторный вывод блокируется правилом `NO_OPEN_DEBT`. Тренерская проводка сторнирована. Бухгалтерии — корректировка в следующей выгрузке.

**E-04. Отклонённая заявка**  
Админ `REJECTED` + причина «справка не подтверждает зачисление». Холд снят. Пользователь видит причину и подаёт новую.

**E-05. Поддельная или просроченная справка**  
Статус документа `REJECTED`. Заявка не одобряется. Аудит просмотра файла.

**E-06. Приглашение принято в день оплаты**  
Advisory lock по `traineeId`. Если accept закоммичен до обработки вебхука — доли 32/50. Если вебхук раньше — доли по состоянию на вебхук (часто 82/0). Пользователь видит фактическую проводку. Пересчёта нет.

**E-07. Расторжение между оплатой и начислением**  
Если «оплата» = редирект, а начисление = вебхук: фиксируется связь на момент **успеха в вебхуке**, не на момент клика «оплатить». UI предупреждает: «ставка определится в момент подтверждения платежа».

**E-08. Удаление тренера**  
Непринятые приглашения `REVOKED`. Активные связи `ENDED`. Журнал начислений сохраняется. Новые платежи подопечных — как самостоятельно. Выгрузка прошлых периодов доступна. Сессии в будущем отменяются статусом `CANCELLED` без удаления.

**E-09. Спор после выгрузки**  
Период `LOCKED`. Обычное оспаривание по сроку уже закрыто; админ создаёт `AttendanceAdjustment` в следующем периоде/выгрузке. Файл прошлой выгрузки не переписывается; версия N+1 содержит поправку.

**E-10. Занятие в последний день периода, отметка после закрытия**  
Окно 2 дня может пересечь lock. Если период занятий уже LOCKED — отметка обычным путём запрещена; только adjustment в следующем экспорте. Если lock ещё нет — отметка в окне допустима.

**E-11. Ошибка перевода банка**  
`PAYOUT_FAILED`, холд жив, админ retry или смена реквизитов через `NEED_INFO`. Двойной выплаты нет за счёт idempotency key.

**E-12. Оплата истекла во время просмотра контента**  
Следующий запрос `/content/:id` или `/media/:id` → 403 `SUBSCRIPTION_EXPIRED`. Плеер останавливается. Кэш `active:` инвалидирован джобом истечения (и TTL≤60 с как предохранитель).

**E-13. Прямая ссылка на медиа без доступа**  
Unsigned object URL не существует. Signed URL просрочен или выдан без права — 403. Пользователь без абонемента не получает подпись.

**E-14. Публикация с переводом только на один язык**  
Материал доступен; недостающий язык — фолбэк ru→ky. В карточке админки — предупреждение. Пользователь на ky при наличии только ru видит русский текст тела (не пустую страницу).

**E-15. Отметки по подопечным без действующей оплаты**  
Технически связь может жить без абонемента. Отметка возможна (занятие — факт работы тренера). Отчёт аномалий показывает такие строки админу. На баланс занимающегося не влияет. В расчётную базу занятие входит как факт проведения.

## 11. Модель данных (Prisma / PostgreSQL)

Денежные поля: `Int` (сомы). Никакого `Float`/`Decimal` для денег **[ДОПУЩЕНИЕ: Int достаточно; при появлении тыйынов — миграция на BigInt тыйынов, сейчас запрещены]**.

Локализуемые справочники: таблица `*I18n` с `locale` (`ru` | `ky`), `@@unique([parentId, locale])`.

## 13. Нефункциональные требования

### 13.1. Безопасность и защита данных

- Номер карты: только токен провайдера и маска.  
- ПИН, паспорт, файлы справок: шифрование at rest **[ДОПУЩЕНИЕ: AES-256-GCM, ключ в KMS/env не в Git]**; доступ по RBAC; каждый просмотр — `SensitiveAccessLog`.  
- Транспорт: TLS.  
- Секреты вебхуков: HMAC, сравнение `timingSafeEqual`.  
- Документы не отдаются по публичному UUID без authz.  
- Контент-редактор не имеет SELECT к таблицам платежей/документов (отдельные DB role или строгий API).  
- Пароли: в MVP OTP, паролей нет. Refresh-токены — httpOnly.  
- Логи приложения: без PAN, OTP, ПИН, тел. частично маскировать.

Персональные данные: ФИО, телефон, email, дата рождения, ПИН, документы об учёбе, маска карты. Хранение: **[ДОПУЩЕНИЕ]** пока действует договор + 3 года журналов (срок уточнить с юристом КР).

Mobile web — полноценный MVP: оплата, баланс, приглашения, отметки (тренер на телефоне). Админские очереди и выгрузки — desktop-first.

## 14. Интеграции

### 14.1. Платёжный шлюз (абстракция)

Провайдер не зафиксирован. Модуль `AcquiringProvider`:

- `createPaymentIntent(amount, idempotencyKey, returnUrl)`  
- `verifyWebhook(signature, body)`  
- `refund(providerPaymentId, amount, idempotencyKey)`  
- `fetchSettlement(from, to)` для сверки  

Обработка вебхуков:

1. Проверка подписи; иначе 401.  
2. Быстрый ответ 200 после persist raw event (чтобы провайдер не засыпал ретраями), обработка асинхронно **[ДОПУЩЕНИЕ: если банк требует синхронной обработки — обрабатывать в запросе < 5 с и всё равно писать raw сначала]**.  
3. Идемпотентность по `eventId`.  
4. Ретраи банка: мы толерантны к at-least-once и к перестановке порядка (статусная машина платежа: не откатывать SUCCEEDED в PENDING).  
5. Таймаут виджета: `PENDING` живёт **[ДОПУЩЕНИЕ]** 30 мин, затем `EXPIRED` если нет успеха; поздний вебхук успеха после EXPIRED — расследовать, не начислять молча (статус `NEEDS_RECONCILIATION`).  
6. Токенизация карт — для автопродления (после MVP) и выплат: токен только от PCI-провайдера.

### 14.2. Выплаты

`PayoutProvider` — раздел 7. Вебхуки статуса перевода: те же правила подписи и идемпотентности. Сверка реестров выплат с `PAID`.

### 14.3. Уведомления

SMS-провайдер КР (OTP). Email. In-app. Шаблоны локализованы. Не слать финансовые детали тренеру.

### 14.4. Бухгалтерия

CSV (UTF-8 BOM) и XLSX. Состав полей — 8.7. Разрез тренер × период. Повторная выгрузка версионируется. Передача: скачивание админом, не email с ПДн **[ДОПУЩЕНИЕ]**.

### 14.5. Медиа

S3-совместимое хранилище + CDN. Загрузка: presigned PUT после authz. Чтение контент-медиа: только через API-подпись после `assertContentAccess`. Документы справок — отдельный bucket, без CDN публичного.

## 16. Критерии приёмки

1. Все пользовательские строки экранов MVP вынесены в ru/ky ресурсы; смена языка без перезахода.  
2. `distribute()` — единственная реализация; тесты на таблицу раздела 5.10 и инварианты.  
3. Успешный платёж без тренера и с тренером даёт ожидаемые доли; сумма долей = платежу.  
4. Начисление занимающемуся приходит без посещений.  
5. Повтор вебхука не удваивает проводки.  
6. Возврат сторнирует все доли; тренер из проводки, не текущий.  
7. Смена тренера не пересчитывает прошлые платежи; следующий платёж — новые доли.  
8. В БД нельзя создать две ACTIVE связи на одного trainee.  
9. API тренера на финансовые URL возвращает 403; в UI тренера нет сумм.  
10. Заявка на вывод фиксирует результаты всех активных правил; смена политики не меняет старую заявку.  
11. Холд уменьшает available; после PAID баланс сходится со журналом.  
12. Отметка вне окна невозможна; удаление отметки невозможно; спор и аудит работают.  
13. После lock периода обычная отметка отклоняется.  
14. Контент тела недоступен без активного периода; каталог виден; медиа без подписи не открывается.  
15. Тренер открывает контент без абонемента.  
16. Публикация контента фиксирует reviewer; дисклеймер на упражнениях.  
17. Выгрузка бухгалтерии строится, повтор идентичен при тех же данных, версия растёт при поправках.  
18. Сверка: эквайринг = три доли за период на тестовом наборе.  
19. Редактор не получает ПДн и финансы.  
20. Документы и маски карт не логируются в открытом виде.

## Риски

### Юридические и налоговые

- Выплата физлицам может квалифицироваться как доход получателя; оператор может стать налоговым агентом. Без юрзаключения формулировки «помощь на образование» недостаточны.  
- Смена модели на грант вузу меняет договор, первичку, НДС/налог с продаж, антиотмывочные процедуры.  
- Баланс не должен выглядеть как привлечение вкладов / электронные деньги без права.  
- Справки об учёбе — ПДн специальной категории по содержанию; нужен правовой основание обработки.  
- Оферта должна явно сказать: начисление не за посещение; ставка зависит от связи с тренером на момент платежа; прошлые периоды не пересчитываются.

### Операционные и финансовые

- Ручная проверка справок при 200k пользователей не масштабируется; без автопредпроверки и массовых операций очередь сорвёт SLA.  
- Chargeback после `PAID` создаёт безнадёжную задолженность (Д-06).  
- Схема 50% без лимита подопечных → фиктивные связи; отчёт нулевой активности и будущий лимит обязательны.  
- Пик 1-го числа: очередь вебхуков, иначе двойные клики и отставание начислений.  
- Расхождение «18%» vs остаток округления при сверке с бизнесом, если считать проценты в Excel без `distribute`.

### Контент о здоровье

- Рекомендации по технике упражнений могут быть связаны с травмой. Нужны: дисклеймер (юр. текст), противопоказания, модерация, быстрое снятие.  
- Ответственность оператора за вред здоровью — **вынести на юридическую экспертизу**; продукт не заменяет врача и очного тренера.  
- Внешние видео (YouTube) могут быть удалены или содержать опасный контент — риск модерации слабее, чем у своего файла.

### Технические

- Партиции журналов и Prisma требуют дисциплины миграций.  
- Кэш активности 60 с + просроченная signed URL — допустимое окно несанкционированного досмотра медиа; TTL подписи держать коротким.  
- Гонка «принятие приглашения / вебхук оплаты» — без lock возможны сюрпризы ставки; lock обязателен.  
- Неполный перевод контента ухудшает ky-аудиторию при фолбэке на ru.

### Продуктовые

- Позиционирование «не кэшбэк» легко сломать в UI и в поддержке.  
- Самостоятельные пользователи не имеют проверяемой тренировочной активности в MVP (completion только в модели).  
- Тренер не видит денег — возможен конфликт ожиданий («где мои 50%»); закрывается регламентом и выгрузкой бухгалтерии, не экраном тренера.
